## 五、缺陷 D4-01（唯一，需修复）

### 现象

登录失败时，**HTTP 状态码为 200，而响应体业务 code 为 401**：

```
POST /api/auth/login  {"username":"admin","password":"wrong"}
  -> HTTP 200  /  biz 401  /  msg=账号或口令不正确

POST /api/auth/login  {"username":"no-such-user","password":"x"}
  -> HTTP 200  /  biz 401
```

### 根因

`app/server.py:1023`

```python
def _http_status(code):
    return {0: 200, 400: 400, 404: 404, 409: 409, 500: 500}.get(code, 200)
```

映射表**缺 401 与 403**，`.get(code, 200)` 的默认值把未知 code 一律降级为 **200**
（"成功"）。`api()` 的三元组返回路径会经它换算：

```python
# app/server.py:915-919
if isinstance(result, tuple) and len(result) == 3:
    code, data, msg = result
    ...
    return self._json(code, data, msg, status=_http_status(code), ...)
```

### 为什么自带 59 项自检没抓到

自检第 35 项测的是 `auth.login()` **函数返回值为 False**，"错误口令被拒=True"——
验证的是**函数层**，从未经过 HTTP 层。自检中唯一断言 401 的是第 59 项
（`demo_switch` 关闭时），而那条路径走的是 `self._json(401, ..., status=401)`
**显式传 status**，绕过了 `_http_status`，所以也是绿的。

**这是一处典型的"函数层测了、传输层没测"的覆盖盲区。**

### 影响面（全量清点）

`_http_status` 只被 `api()` 的**三元组返回**调用。全量清点 22 处此类返回：

| 行 | 业务 code | `_http_status` 结果 | 正确性 |
|---|---|---|---|
| 238 / 367 / 425 / 427 / 429 / 466 / 567 / 570 | 400 | 400 | 正确 |
| 452 / 463 / 474 / 488 / 496 / 522 / 526 / 684 | 404 | 404 | 正确 |
| 476 | 409 | 409 | 正确 |
| **251** | **401** | **200** | **❌ 已实测暴露（登录失败）** |
| **224** | **403** | **200** | **⚠️ 同根因未爆雷**（当前被鉴权闸门提前 403 拦下才没露头；一旦 `/api/auth/accounts` 从权限表摘除即暴露） |

**风险等级：中。** 危害不是"数据泄露"，而是"失败被表述成成功"：
任何按 `resp.ok` / `res.status == 200` 判断的前端或对接方会把**登录失败当登录成功**，
后续请求才因无有效会话而莫名 401，排查成本高。属于**接口契约不一致**类缺陷。

### 建议修复（一行，且顺便消除同类隐患）

```python
def _http_status(code):
    """业务 code → HTTP 状态码。

    0 表示成功；其余按 HTTP 语义原样透传（4xx/5xx）。
    历史实现只映射 400/404/409/500，漏掉 401/403 时会被兜底成 200 ——
    表现为「登录失败返回 HTTP 200」，前端按 resp.ok 判断即误判成功。
    改为白名单兜底 → 语义兜底，杜绝再漏。
    """
    if not code:
        return 200
    code = int(code)
    return code if 400 <= code <= 599 else 500
```

并补一条**传输层**防回归测试（现有自检是函数层，必须补 HTTP 层）：

```
断言：POST /api/auth/login 错口令 → HTTP 状态码 == 401 且 body.code == 401
断言：POST /api/auth/login 不存在用户 → 同
断言：/api/auth/accounts 以非管理员令牌直连 → HTTP 状态码 == 403（不依赖闸门）
```

## 六、架构对照（供演示讲）

P05 与 P02（李奕波个人作品矩阵）刻意做成**两种技术路线**，讲"因地制宜"而不是"一套锤子":

| 维度 | P02 李奕波个人作品矩阵（旗舰） | P05 衡鉴 |
|---|---|---|
| 依赖 | FastAPI + SQLAlchemy + Alembic + Celery + Next.js | **零第三方依赖**（纯标准库） |
| 交付 | Docker Compose + 微服务 | **`python run.py` 即跑** |
| 存储 | PostgreSQL/MySQL | SQLite |
| 前端 | Next.js 16 + React 19 + Tailwind 4 | 原生 HTML/JS 单页 |
| 部署风险 | 需容器运行时 | **拷走一个文件夹就能跑** |
| 适用场景 | 云原生、要横向扩 | 客户现场、内网、无运维 |

> 演示话术：*"P02 证明我能搭云原生全栈；P05 证明我知道什么时候**不该**上云原生——
> 企业内网的合同审查场景，客户不希望为了跑一个工具先装 Docker，
> 所以它零依赖、双击就跑，同时把 RBAC、队列、脱敏、审计留痕这些企业要求一条不少。"*

★ 关键增值点：v2.0 明确写着 **"大模型不参与风险判定，只润色措辞"**。
d4 的升级方向正是**在保持可解释性的前提下**引入 LLM 做二阶段语义复核 ——
这条"确定性召回 + LLM 精判"的演进线，是很有说服力的架构叙事。
