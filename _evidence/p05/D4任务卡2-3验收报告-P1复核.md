## 二、🐞 发现的缺陷 D4-02：配置通路断裂（P1 已修复）

### 现象

跑真实 `boot()` 后，`.env` 里的凭证**注入了 `os.environ`，却到不了应用的 `llm` 配置**：

```
config/app.json:  llm.enabled=false, llm.base_url=""     ← 空
.env:             LLM_BASE_URL_FALLBACK / LLM_API_KEY_FALLBACK 有值
结果：            available() == False，永远走规则模式，Key 白配
```

### 根因

`boot()` 只调了 `dotenv_min.load_dotenv(cfg.root)`（把 .env 变量塞进 `os.environ`），
**但没做任务卡 2 明确要求的映射**：

> 若 llm.base_url 为空，则用 .env 的 LLM_BASE_URL 填充；
> 若环境变量 api_key_env 未设置，用 .env 的 LLM_API_KEY 填入同名环境变量

`load_dotenv` 填的是 `LLM_API_KEY`，而应用读的是 `api_key_env` 指向的 `OPENAI_API_KEY`
与 `llm.base_url` —— **两个命名空间没接通**。

### 为什么 Qoder 的 66/66 没抓到

新增的 4 条自检（#63-#66）全部在**未配 Key 的降级路径**下断言：
验证"降级正确"，**从未验证"配置好之后能真的用起来"**。
这正是任务卡验收第 3 条（配上 Key 后跑一遍）要求、而 Qoder 没做的部分。

### P1 修复

1. `app/dotenv_min.py` 新增 `llm_credentials()` + `apply_llm_config(cfg)`：
   - **主通道优先、备用通道兜底**：`LLM_BASE_URL+LLM_API_KEY` 有值用主通道，
     主通道空则用 `LLM_BASE_URL_FALLBACK+LLM_API_KEY_FALLBACK`
     （本工作区 .env 的主 Key 恰好为空，只有备用通道有值 —— 这条兜底必须存在）
   - **保守填充**：`base_url` 为空才填、key 环境变量为空才填，**绝不覆盖用户显式配置**
   - **不动 `llm.enabled`**：是否启用仍由用户显式决定
2. `app/server.py` `boot()`：`load_dotenv()` 之后调用 `apply_llm_config(cfg)`，
   并把映射结果写进启动审计（凭证来源 / 补全了哪些字段）
3. `config/app.json`：`enabled` → `true`（开箱即用，且未取到凭证时自动降级），
   `model` → `qwen3.8-flash`（百炼可用模型，原 `gpt-4o-mini` 是模板残留），
   note 里写明填充规则与职责边界

## 四、⚠️ 踩坑记录（供后续复用）

**`ingest_upload` 有 SHA256 去重**：上传已审过的文件会直接复用旧案件、**不再触发审查**
（表现为 6ms 返回、快照仍是旧值）。写验证脚本时若复用样本，必须换文件或先清库，
否则会得到"审查没生效"的**假象失败**。P1 第一版 e2e 脚本就中了这一招，误判成代码缺陷。
