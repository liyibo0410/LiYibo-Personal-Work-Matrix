> 编号说明：本条登记为 **D23**。根 `_evidence/INDEX.md` 里 D21 已被「一键启动带起 P01 MySQL 容器」占用
> （根 `agents.md` 也按 D21 引用它），D22 是作品集首页文案重设计，故本条顺延到 D23。

日期：2026-10-14（两轮）· 采集环境：本机 `127.0.0.1:8000`（P02 API，SQLite `api/local_dev.db`）+ `127.0.0.1:3001`（Next 16 dev）+ `127.0.0.1:8800`（统一外壳）

## 问题与根因

用户反馈「商品池商品不能删除」。排查结论：**不是被权限或业务规则拦住，而是删除功能从来没做过**——

| 层 | 原本状态 |
|---|---|
| 后端 `api/app/api/routes/products.py` | 只有 GET / POST / PATCH，**没有 `@router.delete`**（全 api 目录只有 `stores.py:233` 有删除） |
| 前端 `web/src/components/product-row.tsx` | 行内只有一个「进入」链接，**没有删除按钮**（不是 disabled，是根本没渲染） |
| 守卫 / 约束 | 无任何 in_use、409、403 分支；`products` 表无软删除字段 |

第一轮照店铺删除的既有写法补了 `window.confirm()` + 原生 form 提交，用户接着反馈**「点删除没反应」**，
根因见「第二轮」—— 沙箱 iframe 缺 `allow-modals`。

## 第一轮 · 后端与级联

- 后端新增 `DELETE /api/v1/products/{product_id}`（`api/app/api/routes/products.py:350`），
  走 `require_edit_permission`（老板/运营/美工可删，客服 403）+ `get_product_or_404` 的 Workspace 归属校验。
- 测试新增 `api/tests/test_product_delete.py`（4 条）。

### 级联范围（删除商品时真的会清掉什么）

随商品删除：SKU、库存档案、库存流水、平台映射、竞品、竞品监控与快照、创意方案、生成任务与事件、
素材、推广链接与点击、经营数据、复盘报告、广告建议与实验、商品诊断、公开链接解析任务。

**保留**：`agent_runs` / `agent_approvals` —— 只把 `agent_runs.product_id` 置空，不删运行与审批记录。
原因是 `agent_approvals.run_id` 指向 `agent_runs` 且模型里没配外键级联，连带删除会触发约束错误；
用 mapper 内省脚本核过 Product 的级联子图（24 张表可达），唯一的洞就是这一处。

## 第二轮 · 「点删除没反应」

- 外壳 `shell/index.html:347` 的模块 iframe 写的是
  `sandbox="allow-same-origin allow-scripts allow-forms allow-popups allow-downloads"`，**缺 `allow-modals`**。
  按规范，沙箱帧内没有 `allow-modals` 时 `window.confirm()` 不弹窗、**直接返回 `false`**。
- 第一轮的守卫是 `if (!confirmed) event.preventDefault();` → 在 iframe 里恒等于「用户点了取消」→
  浏览器不提交 → 表现为点删除完全没反应。店铺删除按钮（早于本次就有）是同一写法，
  所以它在外壳里其实一直点不动；已 grep 确认全站源码只有这两处用 `confirm()`。

### 修法（两处，各自独立成立）

1. **商品删除改成服务端渲染的两步确认，彻底不依赖 JS**：
   - `web/src/app/(app)/products/[id]/delete/page.tsx`：确认页，读出**真实**连带数量
     （SKU / 平台映射 / 竞品 / 监控 / 创意 / 素材 / 生成任务 / 推广链接 / 经营数据 / 实验 / 建议 / 复盘 / 诊断 /
     解析任务，为 0 的项不展示），并写明「Agent 运行与人工审批记录保留，只解除关联」；
     只读账号（客服）看不到确认按钮，只有清单与只读提示。
   - `web/src/app/(app)/products/[id]/delete/confirm/route.ts`：POST 处理器（`id` 只接受纯数字再拼进 URL）。
     原 `delete/route.ts` 已删除 —— 同一 segment 里 `page.tsx` 与 `route.ts` 不能并存。
   - `components/product-delete-button.tsx` 由「客户端组件 + confirm」改成 `<Link>`（去掉 `"use client"`），
     三个入口位置与 `canDelete` 语义不变。
2. **外壳补 `allow-modals`**：`shell/index.html:347` 的 sandbox 加上该值、并把原因写成注释，
   店铺删除（以及任何模块在 iframe 里的确认弹窗）恢复可用。

### 4. 两步确认端到端（零 JS 环境实测）

新链路是纯链接 + 原生表单，**不需要 React 水合就能跑通**，所以在这台机器唯一可用的自动化环境
（内置浏览器面板未打开 → `document.hidden=true`、DOM 上无 `__react*` 键）里也能完整验证：

| 步骤 | 结果 |
|---|---|
| `/products` 行入口 | 7 个 `<a href="/products/{id}/delete">`，aria-label 与商品名一一对应 |
| 点入口 → 确认页 | 标题「删除商品」；连带数量真实渲染 `SKU:1 竞品:1 推广链接:1`；含 Agent 审计保留说明；表单 `POST /products/7/delete/confirm` |
| 点「确认删除商品」 | 回跳 `/products?product=deleted`，列表提示文案出现，列表回到 6 / 6 件商品 |
| 删除后只读 SQL | product_id=7 的 `products/product_skus/inventory_items/inventory_movements/competitors/promotion_links` 全为 0；`orphan_skus=0`、`orphan_inventory=0` |
| **取消分支**（第一轮没验成那条） | 确认页点「返回商品」→ URL `/products/7`，h1 仍是「取消分支验收商品」，商品未被删 |
| 详情页头入口 | `/products/1` 头部是 `<a href="/products/1/delete">删除商品</a>` |
| 工作台首页行入口 | 与商品池列表同样 7 个链接，和既有 `/stores/{id}/delete` 并列 |
| 外壳回归 | `127.0.0.1:8800/` 正常渲染（作品集首屏在、`.cp-frame-host` 在），iframe `sandbox` 实测已含 `allow-modals` |

演示数据全程未被破坏：验证一律用临时商品（建完即删），两轮跑完商品/店铺都回到原状 6 / 3。

## 未验证 / 边界（不要当成已完成）

- **店铺删除只改了外壳**（补 `allow-modals`），它自己的 `window.confirm` 写法没动。
  「在外壳 iframe 里点店铺删除 → 弹出确认框」这条**没实测**：自动化环境不水合 React，
  真点下去还会删掉演示店铺。要不要把店铺也改成同款两步确认页，等一句话。
- 无截图：内置浏览器无可视 surface（`NATIVE_BROWSER_VIEWPORT_UNAVAILABLE`），证据只有 DOM 结构与数据库计数。
- 覆盖率仍未测量（本模块没配 coverage 插件）。
- PostgreSQL 侧没实机跑：本机 P02 用 SQLite；级联完整性靠 ORM 关系图 + 开 FK 的 SQLite 集成测试证明，
  `docker compose` 起 PG 的复跑没做。
