## 一、决策权与角色（先定这个，后面才不乱）

| 代号 | 身份 | 决策权 | 负责 | **不**负责 |
|---|---|---|---|---|
| **P0** | 李奕波（你） | **最高** —— 否决一切 | 定方向、拍板技术取舍、验收、面试 | 不写代码、不做环境配置 |
| **P1** | 启明（WorkBuddy/我） | **次高** —— 环境与质量线 | 环境治理、依赖、跑通验证、证据采集、文档讲稿、**质量门禁** | 不替你点登录、不擅自改系统配置 |
| **P2** | Qoder | **次高** —— 代码线 | 改造、新功能、重构、补测试 | 不做环境治理、不做最终验收 |

### 冲突裁决规则

```
P1 与 P2 意见不一致
   ├─ 技术可验证（性能/正确性/依赖）→ 谁的主张能被实测验证，听谁的
   ├─ 涉及产品取舍（做不做某功能）→ 各出一页纸方案 → P0 裁
   └─ 涉及红线（删文件、改配置、对外发布）→ 一律停下问 P0

P0 的决定为最终决定，P1/P2 执行时若发现硬阻碍，可回报但不擅自改向
```

## 二、多智能体编制

### P1 侧（启明 · 本工作区可直接调度）

| 智能体 | 类型 | 干什么 | 何时启用 |
|---|---|---|---|
| **勘察员** | Explore | 扫代码，产出「文件:行号」级情报 | 每个 Phase 开工前 |
| **方案设计员** | Plan / general-purpose | 设计算法、词库、架构 | 需要领域设计时 |
| **执行员** | general-purpose | 多步任务、批量操作 | 需要长链路执行 |
| **文档员** | doc-writer | 讲稿、报告、README | 交付文档时 |
| **验证器** | 脚本 + TestClient | 真跑一遍，出证据 | **每个 Phase 收尾必做** |

**调度原则**：勘察与设计**并行**（互不依赖）；执行在勘察结论之后；验证独立于执行（不接受"应该能跑"）。

### P2 侧（Qoder · 你输入 `Q` 唤起）

| 能力 | 用途 |
|---|---|
| **Quest** | Spec 驱动，适合"从零做一个功能" |
| **Agent** | 多文件改造，适合"改现有代码" |
| **Experts** | 多 Agent 协作，适合"大而杂的任务" |
| **Subagent** | `.qoder/agents/*.md` 自定义角色 |
| **Repo Wiki** | 先让它读懂项目，再派活（避免瞎猜） |

### 交战规则（避免互相踩）

1. **P1 产出数据资产**（词库、评测集、配置规范），**P2 消费它**写成代码 —— 天然不冲突
2. **同一时刻同一文件只允许一方改**。P2 改代码时，P1 只读；P1 写数据文件时，P2 不动
3. P2 说"改完了" → **必须** P1 实跑验证（它的"完成"≠ 真跑通）
4. P2 若要删文件/改配置 → **先停下问 P0**（规则里有禁令，但它未必每次守）

## 三、通用工作循环（每个 Phase 都跑这 6 步）

```
① 勘察  P1  扫代码/环境，产出「接入点情报」
   ↓
② 派活  P0  把 P1 的情报 + 执行手册模板 → 粘给 P2
   ↓
③ 编码  P2  实现，产出「改动清单 + 自测命令」
   ↓
④ 验证  P1  实跑一遍，出截图/日志/指标
   ↓
⑤ 存证  P1  落 `_evidence/pXX/`，更新 INDEX.md
   ↓
⑥ 裁决  P0  验收通过 → 下一个 Phase；不通过 → 退回 ③
```

**每步的交付格式见第六节「接口协议」。**

## 六、接口协议（三方交接物格式，必须遵守）

### 6.1 P1 → P2 派活（勘察情报 + 任务）

```
【任务】<一句话>
【背景】<为什么做>
【接入点】（P1 勘察结论，带 文件:行号）
【必须满足】
  1. ...
【禁止】
  - 不改 <文件> 的 <部分>
【验收】<可执行的验证命令 + 期望结果>
```

### 6.2 P2 → P1 交付（改动清单）

```
【改动文件】<路径> —— <改了什么>
【新增文件】<路径>
【自测命令】<命令>
【自测结果】<输出摘要>
【遗留问题】<没做的 / 不确定的>
【是否删除过文件】是/否（若是，必须说明）
```

### 6.3 P1 → P0 汇报（验收结论）

```
【阶段】D<x> <名称>
【结论】通过 / 不通过 / 部分通过
【实测】<命令> → <真实输出>
【证据】_evidence/pXX/...
【风险】<发现的新问题>
【下一步建议】<只给建议，等 P0 决定>
```

### 6.4 P1 → P2 同步（验收标准 + 缺陷类型学 + 项目机制）★ 新增

**时机**：每个阶段验收完成后、下一阶段派活前。
**落点**：`00-总纲/17-P1与P2同步备忘录.md`（持续更新，不新建多份）。

**为什么必须有**：P1 的验收标准如果只在 P1 脑子里，P2 每次都要靠"被退回"来学习它，
返工成本高。同步备忘录把**隐性标准显性化**，让 P2 一次做对。

内容四项固定：
1. **P1 怎么验收**（独立脚本、外部 HTTP 视角、端到端真跑、全树扫描）
2. **缺陷类型学**（历轮发现的模式 + 根因 + 防范，见备忘录第二节）
3. **硬性验收清单**（P2 交付前自检用）
4. **项目特有机制清单**（每个项目独有的工具/约定，避免 P2 重复踩坑）

## 七、熔断与红线（三方共同遵守）

| 触发 | 动作 |
|---|---|
| 要删文件 / 覆盖目录 | **立即停**，报 P0 |
| 要改系统配置（PATH/注册表/环境变量） | **立即停**，报 P0 |
| P2 说"完成了" | P1 必须实跑，**不接受口述** |
| 依赖装不上 / 磁盘告警 / 端口冲突 | 找 P1 |
| 逻辑错、结果不对、接口设计 | 找 P2（Agent 模式，贴报错原文） |
| 拿不准 | 先发 P1，P1 判断该谁做 |
| **P2 说"自检全绿"** | **不等于验收通过** —— 自检是必要条件不是充分条件 |
| **要 push 到远程** | **提交前必查 `.env` 未入暂存区**；禁用 `--force`；不改 hooks |

## 七·五、阶段检查点：GitHub 固化（★ 新增）

每个阶段（D<n> 或里程碑）验收通过后：

```
P1 验收通过 + 产出验收报告
      ↓
P1 主动提醒 P0：「<阶段> 结束，可以让 Qoder 上传 GitHub 固化成果」
      ↓
P0 让 Qoder 执行 `00-总纲/18-GitHub上传指令包.md` 的增量提交指令
      ↓
Qoder 提交前跑 .env 安全检查 → push → 把 git log 贴回
      ↓
P1 把仓库地址/commit 记进进度文档
```

**P1 的提醒是本流程的强制动作**——阶段成果不固化就进下一阶段，
风险是本地误操作/磁盘故障导致返工。详见 `18-GitHub上传指令包.md` 第四节 SOP。
