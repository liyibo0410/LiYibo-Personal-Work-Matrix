## 任务卡 1 —— 修复 D4-01：HTTP 状态码与业务 code 不一致（必做，先做）

```
【背景】
P1 从外部按真实 HTTP 独立验证 P05 时发现一个缺陷，项目的 59 项自带自检没抓到它
（因为自检测的是函数层，没经过 HTTP 传输层）。

【现象】
POST /api/auth/login  {"username":"admin","password":"wrong"}
  -> HTTP 状态码 200，但响应体 {"code":401,"msg":"账号或口令不正确"}
接口"失败"了，HTTP 层却说"成功"。

【根因】
app/server.py:1023
    def _http_status(code):
        return {0: 200, 400: 400, 404: 404, 409: 409, 500: 500}.get(code, 200)
映射表漏了 401 和 403，而 .get(code, 200) 的兜底值把未知 code 一律降级成 200。
api() 的三元组返回路径（app/server.py:915-919）会经它换算 HTTP 状态码。

【影响面（P1 已全量清点 22 处三元组返回）】
- app/server.py:251  return 401  → 实际发出 HTTP 200  ← 已实测暴露（登录失败）
- app/server.py:224  return 403  → 实际发出 HTTP 200  ← 同一颗雷，当前被鉴权闸门
  提前 403 拦下才没露头；一旦 /api/auth/accounts 从权限表摘除就会暴露
其余 400/404/409 路径映射正确，无需改动。

【要做的】
1. 把 _http_status 改成"语义透传 + 白名单兜底"，杜绝再漏：
       def _http_status(code):
           """业务 code → HTTP 状态码。
           0 表示成功；其余按 HTTP 语义原样透传（4xx/5xx）。
           历史实现只映射 400/404/409/500，漏掉 401/403 时会被兜底成 200 ——
           表现为「登录失败返回 HTTP 200」，前端按 resp.ok 判断即误判成功。
           """
           if not code:
               return 200
           code = int(code)
           return code if 400 <= code <= 599 else 500
   （保留 _http_status 这个函数名与签名，调用方不动。）

2. 在 selftest.py 里补【传输层】防回归用例（这是重点，别只改代码）：
   现有 selftest 第 35 项测的是 auth.login() 函数返回 False，
   第 59 项测 401 时是显式传 status=401 绕过了 _http_status —— 两个都覆盖不到本缺陷。
   请新增一条自检项，要求：
   - POST /api/auth/login 错口令 → 断言 【HTTP 状态码】 == 401（不是 200），且 body.code == 401
   - POST /api/auth/login 不存在的用户 → 同上
   - 顺带断言一个 _http_status 的纯函数用例：
     _http_status(401)==401、_http_status(403)==403、_http_status(0)==200、
     _http_status(999)==500（非法值不降级成功）
   自检项数从 59 变成 59+N，输出里要能看到新增项通过。

【验收】
- python run.py --selftest → 全部通过（项数 > 59）
- 用 curl 或等价方式实测：
  POST /api/auth/login 错口令 → HTTP 401
- 不改动任何其他行为（成功的登录仍须 200）

【禁止】
- 不要为了让测试过而改测试预期；不要放宽断言
- 不要顺手"重构"状态码体系（其他接口不动）
```

## 任务卡 2 —— 给规则引擎加 LLM 语义复核（主任务）

````
【背景与设计意图（务必理解再动手）】
衡鉴现在的架构边界写得很明确（见 app/llm.py 文件头）：
    "大模型不参与风险判定。风险识别 100% 由确定性规则引擎（app/review.py）产出，
     大模型只把已确定的命中结果组织成更自然的中文表达。"
这个边界是对的——合同审查要有可解释性、可审计、可复现。

但它也有代价：规则引擎是【关键词/正则】驱动的，误报率高。
例如规则命中"本合同最终解释权归甲方所有"，但如果上下文是
"本合同最终解释权归甲方所有——该条款经双方协商已删除"，规则就误报了。

本次任务是在【不破坏可解释性】的前提下引入 LLM 做【二阶段复核】：
    一阶段：确定性规则引擎全量召回（宁可多报，不能漏报）
    二阶段：LLM 对每一条命中做语义复核，判定 真风险 / 误报 / 需人工确认
两阶段职责分离，判定依据（规则命中原文 + 上下文）全程留痕，所以依然可解释、可审计。

【要做的】

1) 在 app/llm.py 新增一个复核函数（复用已有的 chat() 和 available()，不要新建 HTTP 层）：
       def review_hits(cfg, case, hits, text, paras) -> dict
   返回形如：
       {
         "source": "llm" | "rule-only",
         "reason": "" | "未配置 Key 的具体原因",
         "items": {rule_id: {"verdict": "confirm"|"false_positive"|"need_human",
                             "confidence": 0.0~1.0, "reason": "一句话理由",
                             "source": "llm"|"rule-only"}}
       }
   - 未配置 Key / 调用失败 → source="rule-only"，items 全部 source="rule-only"，verdict 留空，
     绝不能让审查流程报错或中断（对齐现有 polish_summary 的"永不阻断主流程"原则）。
   - 【重要】必须一次批量调用（把所有命中打包成一个请求），不要一条命中一个请求——
     演示时 10 条命中就是 10 次往返，慢且费 token。prompt 里给编号列表，让模型返回 JSON 数组。
   - 【重要】必须要求模型严格输出 JSON，并做健壮解析：
     剥掉 ```json 围栏、容忍前后废话、解析失败就整体降级为 rule-only 而不是抛异常。
   - prompt 要求：只依据给定的合同原文片段判断，不要引入外部法律常识；
     判断不了的标 need_human，不要硬凑结论。

2) 在 app/pipeline.py 接入（精确位置）：
   - 接入点：app/pipeline.py:451 拿到 hits 之后、:472 st.clear_results(case_id) 之前。
     必须在落库前完成复核，因为综合风险是读库算的（:475 st.overall_risk(case_id)）。
   - 把复核结论写回每个 hit：
         h["verify"] = {"verdict": ..., "confidence": ..., "reason": ..., "source": ...}
   - 风险联动（关键）：
     被判为 false_positive 的命中，不要直接从 hits 里删掉（会丢失证据链），
     而是标记 h["verify"]["downgraded"] = True，并让它【不参与】:
        · high 风险计数（:476 highs = [...]）→ 只统计 verdict != "false_positive" 的
        · 拒绝结论的触发（:477 decide_conclusion）
        · 通知里的高风险触发
     也就是说：误报仍展示在报告里（标注"模型判定为误报，待人工确认"），但不影响结论。
   - 复核为 need_human 的，在报告里单列一个"建议人工复核"分组。
   - 审计留痕：仿照 :502 st.audit(case_id, "summary", "llm.polish_summary", ...) 的写法，
     写一条 "review.llm_verify" 审计，记录 source、复核条数、
     confirm/false_positive/need_human 各多少、以及未启用原因。

3) 把复核结果并入 save_parsed 的快照（app/pipeline.py:508 那个 dict）：
   新增 "llm_verify": { ... 上面 review_hits 的返回 ... }，
   并新增一个键 "mode_compare" 里说明复核模式（可复用现有 mode_compare 结构，加一个 "verify" 子块）。

【配置】
app/config/app.json 的 "llm" 段现在长这样：
    {"enabled": false, "base_url": "", "api_key_env": "OPENAI_API_KEY",
     "model": "gpt-4o-mini", "timeout": 30, ...}
请扩展为（保持向后兼容，旧的 enabled/base_url/api_key_env 语义不变）：
    {"enabled": false,
     "base_url": "",                 # 空则由 .env 的 LLM_BASE_URL 填充
     "api_key_env": "OPENAI_API_KEY",
     "model": "gpt-4o-mini",
     "verify_enabled": true,         # 新增：是否开启语义复核（默认开）
     "verify_min_confidence": 0.6,   # 新增：低于该置信度的 false_positive 不降权，转为 need_human
     "timeout": 30}
默认仍是 enabled=false —— 演示时未配 Key 走规则模式，配了才启用。

【怎么读到 .env（这是零依赖项目，没有 python-dotenv）】
本项目根 D:\software\PycharmProjects\面试项目\.env 里已有百炼凭证（变量名见 .env.example）：
    LLM_BASE_URL / LLM_API_KEY                ← 主通道（sk-，按量付费，全模型）
    LLM_MODEL / LLM_MODEL_FAST                ← 模型名
注意：P05 从 projects/p05-contract-review 目录启动，读不到上两级目录的 .env。
请写一个约 30 行的零依赖 .env 解析器（放 app/dotenv_min.py），要求：
  - 从项目根向上最多找 3 级目录，碰到 .env 就加载
  - 只解析 KEY=VALUE，忽略 # 注释与空行，容忍值两端的引号
  - 【不覆盖】已存在的真实环境变量（os.environ 优先，避免污染部署环境）
  - 在做任何 LLM 相关判断之前完成加载（在 app/server.py 的 boot() 里调用一次最合适，
    这样 run.py 启动与 selftest 两条路径都覆盖到）
  - 若 llm.base_url 为空，则用 .env 的 LLM_BASE_URL 填充；
    若环境变量 api_key_env 未设置，用 .env 的 LLM_API_KEY 填入同名环境变量

【验收（必须逐条给出证据）】

2. 【未配 Key 时】跑一份示例合同，报告里有复核区但标注 source=rule-only、

【禁止】
