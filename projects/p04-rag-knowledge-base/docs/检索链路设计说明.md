# 检索链路为什么这样设计

> 本文档基于 `processor/query_processor/` 下的真实实现，说明 BOSS 智库 RAG 检索链路中三个关键设计的动机与收益：HyDE、RRF、BGE-Reranker 断崖检测。

## 1. 链路总览

LangGraph 编排的查询流程（`main_graph.py`）：

```
node_item_name_confirm（主体确认）
   │  条件路由：若无法确认主体（反问/拒答）→ 直接 node_answer_output
   ▼
node_multi_search（分叉）
   ├─► node_search_embedding（BGE-M3 稠密+稀疏 混合检索）
   ├─► node_search_embedding_hyde（HyDE 假设文档检索）
   └─► node_web_search_mcp（MCP 联网搜索）
   ▼
node_join（合并）→ node_rrf（多路融合）→ node_rerank（精排+断崖截断）→ node_answer_output（生成）
```

三路召回并行执行，在 `node_rrf` 融合，再由 Cross-Encoder 精排，最终只把高置信切片交给大模型生成答案。下面分别解释每一层"为什么这样设计"。

---

## 2. HyDE：为什么能提升召回

### 背景问题

用户查询通常是**短查询**（如"为什么不建议放在加热器附近"），而知识库文档是**长文档切片**。短查询的向量在语义空间中容易"飘"：只覆盖了问题的字面意图，缺乏上下文细节，导致与真实文档向量的距离偏远、召回不全。这就是经典的 Query-Document 语义空间不匹配问题。

### 实现（`node_search_embedding_hyde.py`）

1. 先用 LLM 生成一段"假设性文档"（`HYDE_PROMPT`：要求以专家口吻、中文、不超过 300 字、不使用"假设/可能"等不确定词汇）；
2. 将 `rewritten_query + hyde_doc` 拼接后统一向量化（BGE-M3 同时产出稠密 dense 与稀疏 sparse 向量）；
3. 用这个"更丰满"的向量去 Milvus 做混合检索。

### 为什么有效

- 假设文档**补齐了查询缺失的上下文细节**（实体、术语、句式），向量化后更贴近真实文档的分布，显著提高召回率（Context Recall 评估为 1.0）；
- 拼接而非替换：`rewritten_query` 保留用户原始意图，`hyde_doc` 增强语义丰富度，避免 LLM 生成内容"带偏"检索方向；
- 稀疏向量通道同时保留了关键词信号，HyDE 的虚构内容不会完全覆盖原始关键词。

## 3. RRF：为什么比加权分数融合更好

### 背景问题

本链路有三路召回：稠密向量、稀疏向量（Milvus 内 0.8/0.2 融合）、HyDE 路、联网路。不同路的分数**不可直接比较**：稠密距离是余弦相似度量纲，稀疏是 BM25 量纲，HyDE 又是另一套分布。若直接"加权求和"，权重需要针对每一路调参，且对单路分数噪声极敏感。

### 实现（`node_rrf.py`）

采用经典 RRF（Reciprocal Rank Fusion），只使用**排名**而非原始分数：

```
score(chunk) = Σ  权重 / (k + rank)
```

- `k = 60`（平滑常数，抑制排名靠后文档的分数膨胀）；
- 两路权重均为 `1.0`（注释明确："权重都设置 1 就变成了经典 RRF"）；
- 融合后取 `max_results = 5` 进入下游精排。

### 为什么有效

- **尺度无关**：只依赖"这个文档在每路排第几"，天然免疫各检索路分数分布不一致的问题，无需逐路调权；
- **稳健**：一个文档只要在任意一路排名靠前就能获得较高融合分；被多路同时召回时分数叠加，形成"多路共识"信号，比单路高分更可信；
- **实现简洁**：融合逻辑只有字典累加 + 一次排序，O(n) 级开销，无额外服务依赖。

## 4. BGE-Reranker 断崖检测：解决什么痛点

### 背景问题

RRF 融合后仍是"各路排名的加权投票"，**没有真正理解 query 与 doc 的语义相关性**，且本地 RRF 结果与联网结果混在一起。若用固定 TopK（如恒取 5 条）：

- TopK 过大 → 把不相关噪声塞进上下文，污染生成（Faithfulness 下降）；
- TopK 过小 → 可能丢掉真正相关的文档（召回损失）。

相关文档与噪声之间在精排分数上往往存在"断崖"，固定 TopK 无法感知这个边界。

### 实现（`node_rerank.py`）

1. **合并多源**：把本地 RRF 结果（`source="local"`）与联网结果（`source="web"`）统一成 `{content, title, chunk_id, url, source}` 结构；
2. **Cross-Encoder 精排**：用 BGE-Reranker-Large 对 `(rewritten_query, content)` 联合编码打分，得到每条的精确相关性分；
3. **断崖动态截断**：分数降序后，从第 `RERANK_MIN_TOPK=3` 条开始检查相邻分差，只要满足

```
abs_gap >= 0.5（绝对阈值） 或  rel_gap = abs_gap/|score| >= 0.25（相对阈值）
```

即认为出现"相关性断崖"，截断在该位置；否则最多取 `RERANK_MAX_TOPK=10` 条。

### 为什么有效

- **边界自适应**：数据质量好（分数连续）就多给几条，质量差（出现断崖）就少给几条，动态平衡"够用"与"纯净"；
- **双阈值兜底**：绝对阈值防止"0.9 → 0.4"这类大落差被漏检；相对阈值对分数整体偏低但相对跳变明显的场景生效；
- **降级保护**：Reranker 服务不可用时返回 `score=None` 占位并保留原顺序，避免下游节点链式崩溃——检索链路不是"单点失败全挂"。

## 5. 小结

| 环节 | 解决的问题 | 关键参数 |
|------|-----------|---------|
| 混合向量检索 | 语义 + 关键词互补 | dense/sparse = 0.8/0.2，top10 |
| HyDE | 短查询语义稀疏、召回不全 | LLM 生成 ≤300 字假设文档 |
| RRF | 多路分数不可比、权重难调 | k=60，权重 1.0，取 top5 |
| BGE-Reranker 精排 | 排名投票不精确 | Cross-Encoder 联合打分 |
| 断崖检测 | 固定 TopK 塞噪声 / 丢相关 | abs≥0.5 或 rel≥0.25，3~10 条 |

一句话概括：**HyDE 负责"多捞"（提召回），RRF 负责"稳合"（免调权），Reranker + 断崖负责"精筛"（保纯度）**，三层各司其职，最终让大模型只在可信证据上生成答案。
