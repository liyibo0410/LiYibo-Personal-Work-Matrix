# STORY.md — AI 电商运营助手 · 课程结课答辩

## 叙事目标

用 10 分钟让评委相信三件事：

1. 这不是一个"调 API 的 Demo"——它有一条**端到端可验收的运营链路**；
2. 它的核心价值不在"能生成内容"，而在**多 Agent 编排下的可控性**：模型不能乱动数据，高风险动作必须人工审批，且审批能跨时间断点恢复；
3. 结论不是主观感受，而是**脚本退出码 + 可复现报告**（58 项用例全通过、pytest 117 条全绿）。

## 情绪曲线

| 阶段 | 页 | 情绪 | 目的 |
|---|---|---|---|
| 起 | 01-03 | 共鸣 | 运营日常六类动作重复、依赖人工，需要一个"能落地"的助手 |
| 承 | 04-05 | 信服 | 技术栈与分层不是堆砌：鉴权与租户隔离在依赖层收口 |
| 转 | 06-08 | 亮点爆发 | 三个真难点：受控工具网关 / 人工审批+断点恢复 / 可靠执行 |
| 证 | 09-10 | 踏实 | 自研增量与工程化细节、验收方法（58 项 / 9 组 / 退出码判定） |
| 合 | 11-12 | 有力 | 结果：58/58、100%、117 tests；四条最有说服力的实测证据 |
| 收 | 13-14 | 克制 | 安全与合规边界、已知限制与下一步（不吹不藏） |

## 关键数据（全部来自真实执行，禁止改写）

- 验收用例：**58 项**，分 9 组；结果 **PASS 58 / FAIL 0 / SKIP 0**，通过率 **100%**，耗时 **43.1s**
- 回归测试：**pytest 117 passed / 0 failed**（5.33s）；测试文件 28 个
- 数据库迁移：**23 个** Alembic 版本；表 **36 张**
- Agent 规模：**1 协调者 + 8 专家 + 7 工作流**
- 前端治理：飞书设计令牌迁移 **23 个文件 / 约 2100 处 className**
- 四条硬证据（AGT-11 ~ AGT-14）：
  - R2 工作流首次 `next=(approval_gate)` → 批准后 `final_status=completed`，落库 1 次
  - 人工拒绝 → `final_status=rejected`，落库产物 `None`
  - 采纳人工编辑版 → 落库定位 = "人工调整后的商品定位"
  - 质检不通过 → `final_status=quality_failed`，落库 0 次

## 叙事主线一句话

**数据 → 模型生成 → 媒体任务 → 多 Agent 审批 → 系统交付**，每一步都可验收、可追溯、可恢复。
