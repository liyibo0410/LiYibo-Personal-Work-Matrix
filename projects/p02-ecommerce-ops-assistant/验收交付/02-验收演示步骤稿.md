## 1. 一键自动化验收（约 4 分钟，主证据）

### 步骤 1-1 执行脚本

```bash
cd api
..\venv\Scripts\python.exe scripts/acceptance_check.py
```

📸 屏幕保持可见，脚本会实时输出。

### 步骤 1-2 观察执行过程

| 观察点 | 说明（可边指边讲） |
|---|---|
| 建表与建号 | 临时 SQLite 建表 → 引导创建 owner |
| 业务链路 | 店铺 → 商品 → SKU → 库存流水 → 库存汇总 |
| AI 链路 | 诊断（`source=rules` 规则兜底）→ 主图创意策划 |
| Agent 链路 | 创建 Task（202）→ Run → Outbox 同事务 |
| 安全链路 | 401 / 403 / 422 逐条拦截 |

### 步骤 1-3 读取结论

预期输出（脚本末尾）：

```
===== 验收结果：通过 =====
模式: 离线验收（SQLite + inline，临时库 ...）
用例 58：PASS 58 / FAIL 0 / SKIP 0 / WARN 0
通过率 100.0%，耗时 43.1s
报告: ...\api\scripts\acceptance_report.md
```

📸 **截这一屏**——这是验收结论页。

### 步骤 1-4 打开报告

```bash
start api\scripts\acceptance_report.md
```

预期：报告头部含「结论：**通过**」「回归测试：pytest 通过 117 条，失败 0 条」，下方是 58 行逐项结论表。

📸 截报告头部 + 表格前 10 行。

### 步骤 1-5 说明退出码

```bash
echo %ERRORLEVEL%
```

预期：`0`（0=通过，1=有 FAIL，2=脚本自身异常）。

> 一句话总结：**结论不是"我觉得没问题"，而是脚本退出码 0 + 可复现报告。**

## 2. 人工演示：多 Agent 人工审批与断点恢复（核心技术点，约 3 分钟）

### 步骤 2-1 打开接口文档

浏览器打开 <http://127.0.0.1:8000/docs>

### 步骤 2-2 登录拿 token

| 操作 | 预期 |
|---|---|
| 展开 `POST /api/v1/auth/login` → Try it out | — |
| Body 填 `{"email": "admin@local.dev", "password": "LocalDev123!"}` → Execute | 200，`access_token` 有值 |
| 复制 token，点右上角 **Authorize** 粘贴 | 显示已授权 |

### 步骤 2-3 查看 Agent 目录

`GET /api/v1/workspaces/{workspace_id}/agent/catalog`（workspace_id 从 `GET /api/v1/workspaces` 取）

| 预期 | 说明 |
|---|---|
| `coordinator.key = ecommerce_operations_agent` | 1 个协调者只做路由与汇总 |
| `agents` 长度 = 8 | 8 个领域专家 |
| `workflows` 长度 = 7 | 7 条受控工作流 |

📸 截目录返回体。

### 步骤 2-4 创建 Agent Task（异步受理）

`POST /api/v1/workspaces/{workspace_id}/agent/tasks`

Body：
```json
{
  "workflow_key": "inventory_operations",
  "title": "演示·库存运营",
  "context_scope": {"product_id": 1, "store_id": 1}
}
```

| 预期 | 说明 |
|---|---|
| **202 Accepted** | 异步受理，不阻塞请求 |
| `status = queued` | 任务入队 |
| `workflow_version = 1.0.0` | 版本化可追溯 |

📸 截 202 与返回体。

### 步骤 2-5 查看任务与执行记录

| 接口 | 预期 |
|---|---|
| `GET .../agent/tasks/{task_id}` | 200，字段与创建时一致 |
| `GET .../agent/tasks/{task_id}/runs` | 200，≥ 1 条 Run，`thread_id` 为 UUID |

> 讲解点：**Task 是业务意图，Run 是一次可恢复的执行**，两者分离才能支持断点恢复与重试。

### 步骤 2-6 讲清"审批 + 断点恢复"（离线已验证）

指报告中的 AGT-11 ~ AGT-14 四行：

| 用例 | 实测证据 | 讲法 |
|---|---|---|
| AGT-11 | `paused_at=["approval_gate"]` → 恢复后 `final_status=completed`，落库 1 次 | 高风险工作流**必须**停在审批门 |
| AGT-12 | `final_status=rejected`，落库产物 `None` | 人工拒绝则**什么都不落库** |
| AGT-13 | `persisted_positioning="人工调整后的商品定位"` | 采纳的是**人工编辑后**的版本，不是模型原稿 |
| AGT-14 | `final_status=quality_failed`，落库 0 次 | 质检不通过**直接拦住**，不进业务库 |

> 一句话总结：**模型不能直接写库，只有"被批准的产物"才能落库。**

## 5. 演示口径速记（防被问倒）

| 提问 | 回答要点 |
|---|---|
| 结果可复现吗？ | 离线链路隔离了密钥/外部服务/进程状态，同一命令任意机器可复现，退出码即结论 |
| 没配密钥怎么证明 AI 能用？ | 功能链路用「未配置即 400 / 规则兜底」验证分支正确；素材**质量**属在线验收，需真实密钥 |
| 为什么审批要用 LangGraph 的 interrupt？ | 审批是**长事务**：人可能几小时后才点。checkpoint 把状态持久化，同 `thread_id` 恢复，无需重跑模型 |
| 模型会不会乱改数据？ | 不能。所有数据访问经 `tool_gateway` 受控工具白名单 + 脱敏；越权工具直接被策略拒绝（AGT-09） |
| 重复消息会不会重复执行？ | DB 状态幂等 + `agent_leases` 租约 fencing 吸收重复投递；Outbox 与 Task 同事务提交 |
| 多租户会不会串？ | 租户从**成员关系**解析，绝不信任请求体里的 `workspace_id`；路径不一致直接 403、跨租户上下文 422 |

## 6. 演示失败预案

| 现象 | 处置 |
|---|---|
| 脚本报 `ENV-05` FAIL | 临时 SQLite 未删干净，重跑即可（脚本每次会重建） |
| 8000 端口被占 | `docker compose stop api` 释放端口后重启本地后端 |
| 前端 3000 打不开 | 检查 `npm run dev` 是否在跑、`API_CORS_ORIGINS` 是否包含 `http://localhost:3000` |
| 生图/生视频长时间排队 | 本地 inline 模式无后台调度器，失败任务不会自动重跑；改用已完成的成品截图讲解 |
| 现场只能跑一次 | 直接展示 `acceptance_report.md` 与 `acceptance_report.json`，结论等价 |
