# 2026-09-29 工作日志

## 排查「生图一直排队」
- 现象：前端商品页生图任务长期「排队中」，且 start-backend.bat 报 `Errno 10048` 端口占用。
- 定位（直接读 api/local_dev.db 的 generation_jobs 表）：
  - 卡住的 job（id 8/9/12）status=pending，error=`Unsupported image provider: aliyun` → 说明这些任务是**昨晚旧配置下**创建的失败重排任务。
  - 本地模式（TASK_QUEUE_BACKEND=inline）**没有后台调度器**，`process_next_generation_job` 未被周期调用 → 失败后重排成 pending 的 job 永远不会自己重跑，界面就是「排队中」。
  - 10048：用户**双击了两次** start-backend.bat，第二个实例端口占用失败（第一个实例正常）。
  - 另：PID 37456 = `com.docker.backend.exe` 占 `0.0.0.0:8000`（Docker Desktop 行为）；我们的 uvicorn 绑 `127.0.0.1:8000`，两者可共存，不冲突。
- 处置：① 杀掉占用 127.0.0.1:8000 的旧后端（PowerShell `Stop-Process -Id <pid> -Force`；本会话 PowerShell stdout 不回传，结果写文件再 Read）；② 用 sqlite3 把残留 pending job 置为 cancelled；③ 确认 .env.sqlite 为 dashscope 配置；④ 让用户**只启动一次**后端。
- 教训：本地 inline 模式下生成失败会把 job 卡在 pending，需在 UI 取消/重试，或直接改库；不要重复双击启动器。

## 环境备注
- 本会话 Bash 里不能调 `powershell`（被安全策略拦），要用 PowerShell 工具；PowerShell 工具 stdout 不回传，改结果写文件 + Read。

## 「winerror 10013」最终定位（Docker 占 8000）
- 用户机器上跑着项目的 **docker compose 栈**（`docker ps` 从沙箱可执行）：
  - `ecommerce-operation-assistant-api-1` → `0.0.0.0:8000->8000/tcp`（**就是它占住 8000**，导致本地 uvicorn 绑 127.0.0.1:8000 报 `[Errno 13] winerror 10013` 访问权限不允许）
  - 还有 mysql-1(3306)、redis-1、agent-checkpoints-1；另有别的项目 kb-mongo(27017)
  - **没有 web 容器** → 3000 上的 node 是用户本地 `npm run dev`
- 判定证据：`POST /api/v1/auth/login` 用本地账号 `admin@local.dev` 在 8000 返回 **401**（容器用 mysql，无此账号）；本地库走 sqlite local_dev.db 应有此账号 → 说明前端连的是容器后端。
- 容器后端"没密钥"：根目录 `.env` 的 `LLM_*/IMAGE_*/VIDEO_*` 基本为空 → 容器里生成必然失败 → 前端一直「排队」。
- 处置：`docker compose stop api`（可逆）释放 8000 → 本地后端 `scripts/run_local_dev.py` 成功绑定、`/docs` 200、`admin@local.dev` 登录 200。
- 要点：这台机器上 **Docker compose 与本地 dev 抢 8000**，两者只能有一个在跑；要本地联调就先 `docker compose stop api`（或整个 `docker compose down`）。
- `docker-compose.yml`：api `${API_PORT:-8000}:8000`、web `${WEB_PORT:-3000}:3000`，根 `.env` 里 `API_PORT=8000`。

## 终极根因：DB 模型设置覆盖 env
- 现象：本地后端已在跑、`.env.sqlite` 明明写 dashscope，任务仍报 `Unsupported image provider: aliyun`。
- 根因：**`model_provider_settings` 表优先级高于 `.env.sqlite`**。用户在界面「设置」里存过：image=aliyun/compatible-mode/qwen-image-3.0-pro、video=dashscope/compatible-mode/happyhorse-1.1-r2v/duration=2、text 的 api_key 被误填成登录密码 `LocalDev123!`。
- `get_runtime_settings()` 里 DB 行存在就用 DB 值，env 只作无行时回退；**且无缓存（每次直读 DB）→ 改库后无需重启后端**。
- 处置：直接 UPDATE 三行 → image/video = dashscope + base_url `/api/v1` + `wan2.7-image`/`happyhorse-1.1-t2v` + duration5 + 真实 key；text 修回真实 key。已用 `get_runtime_settings()` 复验解析结果全部正确。
- 教训：这套项目的模型配置有**两个来源**（界面「设置」写 DB vs `.env.sqlite`），DB 优先。以后改模型配置务必同时看 DB 那三行，别只改 env。排查生成类问题先查 `generation_jobs.error` + `model_provider_settings`。

## 追加坑：X-DashScope-WorkSpace 头
- 改完 provider 后又报：`The X-DashScope-WorkSpace header value must match the workspace bound to the API key.`
- 原因：`model_provider_settings.workspace_id`（image 行残留 `admin@local.dev`）被 `_dashscope_headers` 发成 `X-DashScope-WorkSpace` 头；该 API key 未绑定 workspace → 拒。
- 处置：`update model_provider_settings set workspace_id=NULL`。清掉后实测 `wan2.7-image` 出图成功。
- 结论：DB 三行要 provider=base_url=api_key=model=size/duration 全对，且 **workspace_id 必须为空**（否则带 workspace 头会被拒）。

## 结果：图文视频全通 + 视频轮询上限
- 清掉 workspace_id 后，UI 生图 #17–#20 全部 succeeded（图存 `api/uploads/generated/*.png`），生图链路端到端打通。
- 视频 `happyhorse-1.1-t2v` 首次报 `DashScope video task timed out`：旧上限 `36×10s=6min` 不够（UI 用的是 35s 完整脚本长提示词，生成更慢）。
- 处置：DB video 行 + `.env.sqlite` 的 `VIDEO_POLL_MAX_ATTEMPTS` 提到 **90**（10s×90=15 分钟）。实测一条 5s 视频 **108.5s** 出片（1080p MP4），链路正常。
- 脚本：`api/scripts/verify_video_poll.py`（走项目服务函数 + 数据库配置，测量真实耗时）。
- 注意：`get_runtime_settings()` 返回 **SimpleNamespace**（不是 pydantic），要改字段用 `copy.copy` + 赋值，不能用 `model_copy`。
- 排查口诀：生图/生视频问题 → 看 `generation_jobs.error` → 看 `model_provider_settings` 三行（provider/base_url/model/workspace_id/poll）→ 二者一致即可。
